# Adding a site

Each feed comes from one YAML file in `sites/`. The file says where to find a site's posts and how to pull each field out of a post's HTML. Feed Me! serves the result at `feeds/<id>.xml` (RSS 2.0) and `feeds/<id>.atom` (Atom 1.0), under the configured `base_path`.

This guide covers the workflow first, then every key a site file accepts.

## Workflow

### 1. Look at the site

Before writing any config, answer three questions by viewing the site's source:

- **How do I find the posts?** Check, in this order:
  1. An RSS or Atom feed, even a summary-only or broken one. It usually carries exact publish dates, which makes the first run much cheaper.
  2. `sitemap.xml`, often linked from `robots.txt`.
  3. The blog's listing page, if it renders links to posts in the served HTML.
- **Where does each field live?** Look for `<script type="application/ld+json">` blocks (usually `BlogPosting` or `Article`), `<meta property="og:…">` tags, and the visible HTML. JSON-LD and meta tags are the most stable. Fall back to CSS selectors for anything they lack.
- **What element holds the article body?** Find the tightest element that holds the text and nothing else, and note any clutter inside it (share buttons, "copy" buttons, ads, newsletter forms).

Feed Me! does not run JavaScript. Everything has to be in the HTML the server sends. Use `curl` or "View Source", not the browser's element inspector.

### 2. Write `sites/<id>.yaml`

The file name must match the `id`. Start from the example below, or copy the existing site file that's closest to yours.

```yaml
id: example-blog
version: 1

channel:
  title: Example Blog
  link: https://example.com/blog
  description: Posts from the Example team.
  language: en-us
  author: Example

schedule:
  timezone: America/New_York

discovery:
  - type: sitemap
    url: https://example.com/sitemap.xml
    include: ['^https://example\.com/blog/[^/?#]+$']

item:
  title:   [jsonld:BlogPosting.headline, meta:og:title, css:h1]
  summary: [jsonld:BlogPosting.description, meta:description]
  author:  [jsonld:BlogPosting.author]
  image:   [jsonld:BlogPosting.image, meta:og:image]
  published:
    sources: [jsonld:BlogPosting.datePublished, 'time:article time']
  updated:
    sources: [jsonld:BlogPosting.dateModified]
  content:
    selector: 'article .post-body'
    exclude: ['script', 'style', 'noscript', 'button']
```

Explain anything unusual in comments, such as why a source comes first or what an `exclude` removes. The existing site files show the style.

### 3. Lint it

```sh
go run ./cmd/feed-me config lint sites/example-blog.yaml
```

Loading is strict. Unknown keys, bad regexes, CSS selectors that don't compile, time layouts that don't round-trip, and missing required fields are all errors, reported as `file:line: key.path: message`. Every problem in the file is reported at once.

### 4. Check extraction against the live site

```sh
go run ./cmd/feed-me check --site example-blog
```

`check` runs discovery, then fetches and extracts the first 5 posts (change this with `--limit`). It stores nothing. For each post it prints every field, the source that produced it, and any warnings. It exits non-zero if a post has no title or no content.

Useful flags:

- `--url <post URL>` checks specific posts instead of discovered ones. You can repeat it. Pick posts that stress the config: one with code blocks, one with images or video, one with several authors, and an old one from a different template.
- `--json` prints the full results as JSON, including the extracted body HTML.

Change the config and rerun until every field comes from the source you expect and no warnings remain.

### 5. Build the feed and validate it

```sh
go run ./cmd/feed-me build --site example-blog
go run ./cmd/feed-me validate --site example-blog --w3c
```

`build` does a real run: it fetches, stores items in the SQLite store, and writes static feeds to `out_dir`. The first run fetches every discovered post at the rate limit, unless discovery supplies dates (see [`max_items`](#schedule)). `validate` renders the feeds from the store and checks them. `--w3c` also sends them to the W3C Feed Validation Service. Open the feed in a reader or two to check how the body renders.

### 6. Add fixtures and tests

Every site has offline tests under `testdata/<id>/`:

- The discovery document (`sitemap.xml`, `rss.xml` or listing page HTML) and `robots.txt`.
- A handful of representative posts in `testdata/<id>/posts/<slug>.html`, saved with `curl` so they match what Feed Me! sees.
- `check.golden.json`, generated by the test.

Wire them up in `cmd/feed-me/check_test.go`:

1. Map the discovery and `robots.txt` URLs to their files in `fixtures()`, and add the post URL pattern to its loop.
2. Add a `TestCheck<Site>` function modeled on the others. It should assert the title, author and published date of each fixture, plus that nothing is missing or warned about.
3. Run `go test ./cmd/feed-me -update` to write the golden file, and review it.

Trim the saved pages only if they are very large, and keep everything the config's selectors and sources depend on.

### 7. Update the README

Add the site to the "Supported sites" table in `README.md`.

Site files are baked into the Docker image at `/sites`, and `compose.yaml` mounts the repo's `sites/` over them. A new or edited site file only needs a restart to take effect.

## Configuration reference

A site file has these top-level keys:

| Key | Required | Description |
| --- | --- | --- |
| `id` | yes | The site's identifier. It must match `[a-z0-9-]+` and the file name (`<id>.yaml`), and be unique. It becomes the feed path: `feeds/<id>.xml`. |
| `version` | yes | Schema version. Always `1`. |
| [`channel`](#channel) | yes | Feed-level metadata. |
| [`schedule`](#schedule) | no | How often to crawl and how many items to publish. |
| [`fetch`](#fetch) | no | Per-site HTTP settings. Defaults come from `feed-me.yaml`. |
| [`discovery`](#discovery) | yes | A list of one or more strategies that find post URLs. |
| [`item`](#item) | yes | How to extract each field from a post page. |

### Value formats

- **Duration:** a Go duration, such as `30s`, `1h` or `336h`. Days aren't supported, so write 14 days as `336h`. It must be positive.
- **Rate:** `N/unit`, where the unit is `s`, `m`, `h` or a duration. For example, `1/s`, `30/m`, or `1/2s` for one request every two seconds.
- **Regex:** Go [RE2 syntax](https://github.com/google/re2/wiki/Syntax). Quote regexes in single quotes so backslashes survive YAML.
- **CSS selector:** anything [cascadia](https://github.com/andybalholm/cascadia) compiles, including `:not()`, `:has()`, attribute selectors and comma-separated groups. Quote any selector that contains `#`, `:`, `[` or `,`, or YAML may misread it.
- **Time layout:** a Go layout written in terms of the reference time `Mon Jan 2 15:04:05 MST 2006`, such as `'Jan 2, 2006'`. It must include a year and round-trip.

### `channel`

| Key | Required | Default | Description |
| --- | --- | --- | --- |
| `title` | yes | | The feed's title. |
| `link` | yes | | The human-facing site URL. It must be an absolute http(s) URL. |
| `description` | yes | | A one-line description. RSS requires one. |
| `language` | no | | A language tag such as `en-us`. |
| `image` | no | | An absolute URL for the channel image. |
| `author` | no | | The author used for items that have none of their own. |
| `ttl` | no | | A hint to readers about how often to poll, in minutes, emitted as `<ttl>`. It doesn't affect crawling. |

### `schedule`

| Key | Default | Description |
| --- | --- | --- |
| `interval` | `1h` | How often `feed-me run` crawls the site. |
| `refresh_window` | `336h` (14 days) | Known items published within this window are fetched again on each crawl, to pick up edits. The fetches are conditional GETs, so an unchanged page is cheap. |
| `max_items` | `50` | How many of the newest items the feed contains. When discovery supplies publish dates (a `feed` strategy), the first run fetches only this many of the newest posts instead of every one. |
| `timezone` | `UTC` | An IANA timezone name. Dates with no zone are read in it, and date-only values get their time of day from it (see [Dates](#published-and-updated)). |

### `fetch`

| Key | Default | Description |
| --- | --- | --- |
| `rate` | from `feed-me.yaml` (`1/s`) | The request rate limit per host. |
| `timeout` | from `feed-me.yaml` (`20s`) | The timeout for each request. |
| `headers` | none | Extra request headers, as a map. They go only to the hosts of this site's discovery URLs and any hosts in `header_hosts`, and are removed on redirects elsewhere. You can't set headers Feed Me! manages itself, such as `User-Agent` and the conditional-GET validators. Use `user_agent` in `feed-me.yaml` to change the User-Agent. |
| `header_hosts` | none | Extra hosts, as `host` or `host:port`, that also receive `headers`. Matching is exact, so `example.com` does not cover `www.example.com`. |
| `respect_robots` | `true` | Whether to obey the site's `robots.txt`. |

Fetches reach only public IP addresses unless `fetch.allow_private_networks` is set in `feed-me.yaml`.

### `discovery`

A list of strategies. They run in order, and their results are merged and deduplicated by URL. When two strategies find the same URL, each listing hint comes from the first strategy that supplied it. URL fragments are dropped.

Keys every strategy accepts:

| Key | Description |
| --- | --- |
| `type` | Required. `sitemap`, `feed`, `index` or `links`. |
| `url` | Required for every type except `links`. An absolute http(s) URL. |
| `include` | A list of regexes. A discovered URL is kept only if it matches at least one. With no `include`, every URL is kept. |
| `exclude` | A list of regexes. A URL that matches any of them is dropped. `exclude` wins over `include`. |

Anchor `include` patterns (`^https://example\.com/blog/[^/?#]+$`) so tag, category, author and pagination pages don't slip through as posts.

Setting a key that belongs to a different type is an error.

#### `type: sitemap`

Reads a `sitemap.xml` or a sitemap index, including gzipped ones, and follows child sitemaps on the same host.

| Key | Default | Description |
| --- | --- | --- |
| `trust_lastmod` | `false` | Also fetch a known post again when its `<lastmod>` is later than its last fetch. Leave this off for sites that stamp every URL with the build date. |

Listing hints supplied: `lastmod`.

Sitemaps rarely carry publish dates, so the first run fetches every matching post to find the newest ones. Every item is kept in the store afterward, so this happens only once.

#### `type: feed`

Reads an existing RSS or Atom feed and uses its items as the list of posts. Feed Me! still fetches each post's page for the full text. This strategy suits sites whose feeds are summary-only or broken.

Listing hints supplied: `published`, `updated`, `title`, `description`, `author`, `category`.

#### `type: index`

Fetches a listing page and collects post links with a CSS selector, optionally following "next page" links.

| Key | Default | Description |
| --- | --- | --- |
| `link_selector` | required | Selects the `<a>` elements that link to posts. |
| `next_selector` | none | Selects the link to the next listing page. Next pages must be on the same host. |
| `max_pages` | `5` | The most listing pages to read. |

Listing hints supplied: `title` (each link's text).

An index sees only the posts listed on the pages it reads. Use it when a sitemap would mean fetching thousands of pages, or when it's the only option.

#### `type: links`

A fixed list of post URLs, mostly for testing.

| Key | Description |
| --- | --- |
| `urls` | Required. A list of absolute http(s) URLs. It replaces `url`, which you can't set for this type. |

Listing hints supplied: none.

### `item`

Each field is a list of **sources**, tried in order. The first source that yields a non-empty value wins. Put the most reliable source first and fallbacks after it.

| Key | Required | Default | Description |
| --- | --- | --- | --- |
| `canonical` | no | `[meta:og:url, 'css:link[rel=canonical]@href', request]` | The post's permanent URL. It becomes the item's link and, by default, its GUID. If no source matches, the fetched URL is used. |
| `title` | yes | | The item title. |
| `summary` | no | | The item's `<description>`. Without one, the first ~300 characters of the body's plain text are used. |
| `author` | no | | Every value from the winning source is an author. Duplicates are removed, and the rest are joined as "A", "A and B" or "A, B, and C". Falls back to `channel.author`. |
| `image` | no | | The lead image URL. It's emitted as `<media:content>`, and as an `<enclosure>` too when `enclosure: true`. |
| `categories` | no | | Every value from the winning source becomes a `<category>`, with duplicates removed. |
| `published` | no | | See [below](#published-and-updated). |
| `updated` | no | | See [below](#published-and-updated). |
| [`content`](#content) | yes | | Selects the article body. |
| `guid` | no | `permalink` | `permalink` uses the canonical URL as the GUID. `stable-hash` uses a UUIDv5 of the first-seen URL, for sites whose canonical URLs might change. Changing this for a live feed will duplicate every item in readers. |
| `enclosure` | no | `false` | Also emit an RSS `<enclosure>` for the lead image. |

URL-valued fields (`canonical` and `image`) are resolved against the page URL, or its `<base href>`, and must end up as http(s). Text values have their whitespace collapsed and invisible "stega" characters removed.

#### Sources

A source is a string of the form `kind:expression`, with an optional `@attribute` for some kinds. Quote sources that contain `#`, `[`, `,` or `: `.

| Kind | Example | What it reads |
| --- | --- | --- |
| `jsonld:<Type>.<path>` | `jsonld:BlogPosting.author.name` | JSON-LD objects whose `@type` is `<Type>`, wherever they appear on the page, including inside `@graph`, arrays and nested objects. The path is a dotted list of properties, and arrays fan out into several values. When the path ends at an object, its `url`, `name`, `@id` or `@value` is used, in that order, so `jsonld:BlogPosting.author` and `jsonld:BlogPosting.image` work directly. HTML entities in strings are decoded. |
| `meta:<name>` | `meta:og:title`, `meta:article:published_time` | The `content` of the first `<meta>` tag whose `property`, `name` or `itemprop` matches, case-insensitively. It yields at most one value. |
| `css:<selector>[@attr]` | `css:h1`, `'css:.byline a'`, `'css:article img@src'` | Every element the selector matches. Without `@attr` it reads each element's text. With it, it reads that attribute. |
| `time:<selector>[@attr]` | `'time:article time'` | Like `css`, but `@attr` defaults to `datetime`, falling back to the element's text when the attribute is missing. Meant for dates. |
| `url:<regex>` | `'url:/(\d{4})/(\d{2})/(\d{2})/'` | A match against the fetched URL. With capture groups, the non-empty groups are joined with `-`, so the example yields `2026-09-17`. Without groups, it yields the whole match. |
| `listing:<field>` | `listing:published` | A hint captured by discovery. The field must be one that one of the site's discovery strategies supplies: `published`, `updated`, `title`, `description`, `author`, `category` (from `feed`), `lastmod` (from `sitemap`) or `title` (from `index`). Linting fails otherwise. |
| `request` | `request` | The URL that was fetched. It takes no expression. |

Single-valued fields (`canonical`, `title`, `summary`, `image`) use the winning source's first value. `author` and `categories` use all of them.

#### `published` and `updated`

```yaml
published:
  sources: [jsonld:BlogPosting.datePublished, 'css:.post-date']
  layouts: ['Jan 2, 2006', 'January 2, 2006']
```

| Key | Description |
| --- | --- |
| `sources` | Sources, as above. Each value is parsed in turn until one parses. A value that doesn't parse produces a warning and falls through to the next. For `jsonld`, every matching object is tried, not just the first. |
| `layouts` | Extra Go time layouts, tried after the built-in ones. You can only set them alongside `sources`. |

The built-in layouts cover RFC 3339 / ISO 8601, including date-only `2006-01-02` and forms without a zone, and the RFC 1123/822/850 formats used in feeds. Add `layouts` only for human-readable dates such as `Sep 17, 2026`.

How dates are treated:

- A value with no zone is read in `schedule.timezone`.
- A **date-only** value needs a time of day. If Feed Me! first sees the post on that same day in the site's timezone, it uses the first-seen time. Otherwise it uses midnight local time, with posts from the same day kept in discovery order.
- A post's published time is frozen once stored, so it doesn't jump around in readers. It changes only if the site's own date moves to a different day.
- With no publish date at all, the post gets its first-seen time and `check` warns about it.
- `updated` is emitted in Atom when it's later than `published`. RSS has no per-item updated field.

#### `content`

| Key | Default | Description |
| --- | --- | --- |
| `selector` | required | Selects the article body. The inner HTML of every match is kept, in document order. A match nested inside another is skipped, and matches with no text and no images or video are dropped. |
| `exclude` | none | A list of selectors for nodes to remove from the body before it's cleaned, such as `script`, `style`, `button`, share widgets and "copy" labels. |
| `keep_first_image` | `true` | If the body has no images, put the item's lead `image` at the top. |
| `keep_video` | `false` | Keep `<video>` elements. Video and YouTube/Vimeo embeds are always replaced with a poster image and a "Watch video" link, because readers handle them inconsistently. This keeps the `<video>` alongside that link. |

After extraction, the body is cleaned up for readers: URLs (including `srcset`) are made absolute, lazy-loaded images are fixed, and the HTML is sanitized. Sanitizing removes `class`, `style`, `id`, event handlers, inline `<svg>` and anything outside a standard set of formatting, list, table, figure, code, image and link tags. So `exclude` should target clutter, not styling. Styling won't survive anyway.
